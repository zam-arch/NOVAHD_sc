## Causas de la pantalla de descarga detenida

- La configuración heredada apuntaba a `example.com`. La petición directa al manifiesto devolvió HTTP 404 con verificación TLS correcta. El manifiesto de ejemplo siempre se cargaba primero, con SHA-256 y tamaños inventados. El diálogo anterior tampoco persistía una URL elegida por el usuario. No encontré un servidor autorizado disponible para este proyecto; la URL inicial de Recovery queda vacía.
- La aplicación tenía `INTERNET`; las evidencias anteriores no apuntan a un problema de permisos de red. La rama anterior sí tenía otros problemas de integración. La actividad declaraba una referencia a `downloadService` pero nunca la enlazaba ni instalaba el callback. `onBind()` devolvía `null`. La actividad enviaba solo el primer archivo, pasaba de inmediato a Descargando y no recibía el progreso ni el error del servicio. La versión de `development` también tenía mal declarado el nombre de clase del servicio y omitía `WAKE_LOCK`. Esas condiciones explican tanto el 404 al intentar acceder a la fuente como la pantalla inmóvil aunque hubiera espacio. No se dispone de un logcat del teléfono para ordenar los síntomas observados allí.
- El selector previo cerraba borrando la carpeta existente y lanzando una excepción provisional. La extracción ZIP no limitaba las rutas al destino y el gestor escribía en el área interna mientras el motor prefería la externa. El mismo árbol declaraba un tema y un icono inexistentes, XML inválido, fuentes no UTF‑8, estados Java sin definición y lambdas con variables mutables. Su flujo CI también pedía una plataforma 26 para compilar un módulo configurado para 34, silenciaba errores nativos y usaba `--runtime-only` en trabajos limpios que carecían de los objetos recompilados.

## Archivos y alcance de la reparación

- `CampaignManager.java` y `ResourceManagerActivity.java` conectan las operaciones y su estado visible. La lógica usa un único ejecutor en el proceso y conserva el fragmento de descarga en disco. Al reabrir detecta el fragmento y ofrece continuar. La interfaz reaprovecha el layout existente y el diálogo guarda una URL HTTPS directa proporcionada por el usuario.
- `CampaignDownload.java` usa los certificados y la confianza normales de Android, con tiempos de conexión y lectura de ocho segundos, tres intentos, mensajes HTTP y reinicio cuando cambia el recurso. Verifica el tamaño, `ETag` fuerte, `Range`, `If-Range` y `Content-Range`. Un servidor que omite un validador fuerte permite reiniciar una descarga parcial. La descarga vive mientras existe el proceso y vuelve a ofrecer reanudación tras una interrupción.
- `CampaignFiles.java` verifica el tamaño y SHA-256 de cada entrada, usa almacenamiento privado y publica una carpeta verificada con un cambio atómico de nombre. Valida espacio y limpia las instalaciones interrumpidas, preservando la carpeta previa. Instala los recursos incluidos en un APK Recovery autorizado o importa un IPA, ZIP o APK 0.4 legítimo mediante `ACTION_OPEN_DOCUMENT`. Solo instala las rutas de referencia. Los archivos dañados deben venir de un archivo compatible o del bundle incluido. Se retiraron la cola y el servicio sin comunicación, el manifiesto de ejemplo y las utilidades de extracción anteriores.
- `runtime/android_main.c` ajusta únicamente la ruta del bundle para el arranque gestionado. Conserva el directorio de partidas que usa la versión original. Si la versión 0.4 ya extrajo sus archivos y la aplicación conserva acceso al directorio, el gestor puede migrar ese bundle tras verificar sus hashes. EGL, GLES 1.1, el runtime OpenAL con salida AAudio, el acelerómetro y los controles provienen del original.
- `app/build.gradle`, `gradlew`, `.gitignore` y `build-apk.yml` fijan el flujo Gradle y rechazan el empaquetado si faltan las entradas del juego. `build_apk.py --native-only` conserva el recompilador 0.4 y enlaza la biblioteca para el arranque gestionado. `prepare_recovery.py` valida los archivos legítimos. `verify_recovery_apk.py` exige AArch64, alineación de LOAD de 16 KiB, el hash de la imagen de referencia y los 44 recursos. `check_android_runtime.sh` compila el runtime y el glue de NativeActivity con el NDK 28.2.13676358. El build común usa Gradle 8.5, Android SDK 34, min SDK 26 y target SDK 34.

## Pruebas y bloqueo de entrega

- Las tareas Java de debug y release compilaron localmente con Gradle y SDK 34. Las pruebas JVM verificaron primera instalación, corrupción de igual tamaño, rechazo de hash incorrecto, restauración tras renombrado interrumpido, cancelación y espacio insuficiente. Para HTTP usaron respuestas simuladas, incluidos corte, persistencia, reanudación con rango y 404.
- La prueba JVM con el APK oficial, conservado localmente, verificó los 44 archivos, detectó la pérdida de un paquete de nivel y lo reparó. No se publicó el APK oficial, su biblioteca ni sus recursos.
- Falta el archivo legítimo `Payload/NovaHD.app/NovaHD`, Mach-O ARMv6 de la versión iPad 1.0.6 compatible con los recursos. Ni el ZIP de código fuente ni el APK oficial contienen ese ejecutable. Falta también una fuente HTTPS autorizada si se elige la descarga. Sin el Mach-O no se puede ejecutar la recompilación completa, generar y firmar un APK Recovery verificable ni probar el juego en un dispositivo.
- El workflow completo está disponible mediante `workflow_dispatch` en un repositorio privado autorizado, con `build_complete` y el entorno `authorized-recovery`. Las entradas son `NOVA_IPA_HTTPS_URL` y `NOVA_IPA_SHA256`, con una URL HTTPS directa al IPA legítimo, sin redirecciones. Opcionalmente admite la clave de firma y sus secretos documentados en el workflow. El job valida el IPA, recompila, ensambla y publica `nova-hd-android-0.5-recovery-arm64` en ese repositorio privado. El workflow público solo valida código y rechaza APK incompletos.
- Pendiente en un teléfono ARM64, instalar un APK completo, arrancar la campaña, comprobar sonido, controles y partidas, y probar reinicio, falta de espacio, corte de red real y modo avión. La validación JVM y la inspección estática del APK oficial no sustituyen esas pruebas.
